# Declaration Assistant System ArchitectureThe Declaration Assistant helps insurance advisors quickly find the right screening question to ask a customer about a pre-existing medical condition (PED) when setting up a health insurance policy. Instead of manually searching through lengthy policy documents, the advisor simply types in the condition, and the system instantly works out which question applies for that specific insurance plan. This document gives a plain-language overview of how the system works behind the scenes, followed by more detailed diagrams for reference.## **High Level Engine Architecture**The request lifecycle is designed around a strict separation of concerns, ensuring that each layer—from the user interface to the database—performs a specialized role. When an advisor interacts with the system, the data travels through four primary stages to transform a raw input into an actionable screening question:1. **React Frontend (UI Layer):** The journey begins when the advisor enters a medical condition. The React application captures this interaction and initiates the request, providing a seamless interface for data entry and results display.2. **Node.js Backend (API Layer):** The request is transmitted via REST API calls to the Node.js server. This layer manages authentication, session state, and secure routing, acting as the gateway between the user and the system's core intelligence.3. **Declaration Engine (Logic Layer):** The engine serves as the central decision-maker. It applies the core business logic, resolves medical aliases, and determines the optimal mapping strategy by orchestrating data retrieval and evaluation.4. **PostgreSQL Database (Data Layer):** Finally, the system queries the persistent storage to retrieve the "Source of Truth" for policy rules and medical mappings. Once the data is retrieved, the engine evaluates it to return a precise, intelligent response back to the frontend.&#x20;                 USER  │  ▼  React Frontend (Web App UI)  │  ▼  REST API Calls  │  ▼  Node.js Backend (server.ts)  │  ▼  DECLARATION ENGINE (Decision Maker)  │  ▼  PostgreSQL Database (Source of Truth)  │  ▼  Query Application Data Tables  │  ▼DECLARATION ENGINE (Evaluates the Retrieved Data)  │  ▼  Is Mapping Complete?  │  ┌───────────────────┬──────────┐  │                              │  YES                            NO  │                              │  ▼                              ▼  Return Response                Query Gemini AI  │  ▼  AI Suggestion / Review  │  ▼  DECLARATION ENGINE (Final Decision)  │  ▼  Return Response to User**PED Mapping Flow Architecture**  When an advisor enters a PED, the system needs to decide which screening question to show. Here is a plain-language summary of what each piece does.### **React Frontend**Presents the UI and sends user requests.### **Node.js Backend**Authentication, API layer, routing, and session management.### **Declaration Engine**Business logic, normalization, alias resolution, P0→P3 processing, orchestration, and final decision making.### **PostgreSQL**Primary source of truth for PED Repository, aliases, categories, plan mappings, overrides, users, activity logs, and governance data.### **Gemini AI**Fallback AI assistance used only when database-driven resolution is insufficient or AI review is required.## **Core Principles**Regardless of how a request is handled, a few core rules always hold true:* PostgreSQL is the single runtime source of truth for business data.* The Declaration Engine is the only component that makes mapping decisions.* Gemini AI never overrides approved repository data.* Business logic lives in the engine; business data lives in PostgreSQL.**Application Database**Behind the scenes, the system relies on a single, central database to store everything it needs to make accurate decisions - from the list of known medical conditions to each insurance plan's specific rules. Keeping all of this in one place ensures the advisor always sees consistent, up-to-date information. Specifically, the database stores the following:1. PED Repository2. PED Aliases3. Categories4. Plan Configurations5. Plan Overrides6. AI Memory7. AI Mapping Review8. Mapping History9. Collision Repository10. Users \& Roles11. Activity Log12. Search History13.
